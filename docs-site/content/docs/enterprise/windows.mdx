The standalone Windows profile installs four Service Control Manager services
under `C:\Program Files\Cisco\DefenseClaw` and `C:\ProgramData\Cisco\DefenseClaw`.
It does not need Cisco Secure Client and never creates the Secure Client
credential broker.

## Services

| Service | Identity | Role |
| --- | --- | --- |
| `DefenseClawGateway` | `NT SERVICE\DefenseClawGateway` (restricted service SID) | Runs the policy engine and the hook API; reads config and authorization, writes only its runtime state and logs |
| `DefenseClawSensorHelper` | LocalSystem, `SeChangeNotifyPrivilege` only | Answers fixed AI Discovery acquisition requests; the gateway depends on it |
| `DefenseClawHookGuardian` | LocalSystem, explicit privilege list | Installs and repairs each enrolled user's hooks under that user's own token; merges DefenseClaw's entries into vendor machine policy |
| `DefenseClawHookEnumerator` | LocalSystem | Finds eligible interactive profiles (local, domain, and Microsoft Entra ID accounts) and publishes the protected target manifest |

Standard users get query-only access to all four services. Every service
restarts indefinitely after a failure.

## Requirements

- 64-bit native Windows 10-family or newer, including Windows Server 2019 or
  later (the same floor as the [per-user package](/docs/get-started/windows/install-lifecycle)).
  Native ARM64 and 32-bit processes are refused.
- **PowerShell 7** (stable 7.x) installed machine-wide from Microsoft's MSI.
  The lifecycle resolves `pwsh.exe` only from
  `HKLM\SOFTWARE\Microsoft\PowerShellCore\InstalledVersions`, requires it under
  Program Files with administrator-only folders and a valid Microsoft
  signature, and ignores `PATH`. Without it the lifecycle stops with
  `powershell7_required`. Windows PowerShell 5.1 is not used by the
  standalone profile.
- Full Language Mode for the lifecycle. Under Constrained Language Mode or a
  WDAC script policy, allow the DefenseClaw signer (or your re-signing
  certificate) first.
- An elevated administrator or SYSTEM context (for example the Intune
  Management Extension).

## Payload trust

Pick one trust mode with `--trust-mode`; `enterprise.trust` in the config
can only narrow it (see below):

| Mode | Use it when | How it works |
| --- | --- | --- |
| `authenticode` (default) | You have a signed release, or you re-sign the payload with your own certificate | Every binary and script must carry a valid signature. Add `--allowed-signer <sha256-thumbprint>` (repeatable) to accept only specific signers |
| `hash_pinned` | You deploy an unsigned build | Pass `--payload-manifest <file>`: an administrator-owned JSON file of SHA-256 digests (`{"schema_version":1,"files":{"<name>":"<sha256>"}}`). The CLI verifies the installer, module and payload before PowerShell starts |

`enterprise.trust.mode: authenticode` in the config refuses a hash-pinned
run with `1639`, and so does a run over a deployment that was installed
hash-pinned: without a payload manifest the lifecycle re-admits that
deployment's payload by its recorded pins. Leave the mode unset or set
`hash_pinned` while you deploy unsigned builds.
`enterprise.trust.allowed_signers` works like `--allowed-signer`; when both
are given they must list the same thumbprints.

Hash-pinned payloads do not satisfy WDAC or AppLocker rules that require a
publisher. Sign or re-sign when those rules are in force.

## Install or converge

`ensure` is the one command an MDM needs. It installs when nothing is
installed, upgrades an older deployment, reconfigures after a config change,
repairs after a failed verify, and otherwise does nothing.

```powershell title="Elevated PowerShell 7"
$Stage = 'C:\ProgramData\DefenseClaw-Staging\<version>'
& "$Stage\defenseclaw.exe" enterprise windows ensure `
  --profile standalone `
  --config "$Stage\config.yaml" `
  --trust-mode hash_pinned `
  --payload-manifest "$Stage\payload-trust.json" `
  --json
```

The stage directory must be administrator-owned and not writable by users.
The installer enumerates eligible profiles itself; administrators do not
author `targets.yaml`. With `enterprise.enrollment.mode: manifest` you publish
`targets.yaml` yourself: pass it with `--manifest`, or a first install stops
with `invalid_arguments`.

Exit codes follow Windows Installer conventions so MDM retry logic works:

| Code | Meaning |
| --- | --- |
| `0` | Success or no change |
| `1603` | Failure; the transaction rolled back, or stayed pending when the rollback could not finish (see [Recover a pending transaction](#recover-a-pending-transaction)) |
| `1618` | Another lifecycle run holds the lock; retry later |
| `1639` | Invalid arguments |
| `3010` | Reserved for a required restart |

## Detection and support

After every successful mutation the lifecycle writes:

- `HKLM\SOFTWARE\Cisco\DefenseClaw\Enterprise` with the installed version
  (use it for MDM registry detection rules) and `DisableSelfUpdate`;
- an Add/Remove Programs entry, `CiscoDefenseClawEnterprise`;
- events from the `DefenseClaw Enterprise` source in the Application log;
- `%WINDIR%\Logs\DefenseClaw\enterprise-lifecycle.log` and
  `last-result.json`, readable by users for support.

These are for detection only. Enforcement and `verify` never trust them.

## Verify, repair, remove

```powershell
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise windows status --json
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise windows verify --json
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise windows repair --json
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise windows uninstall --json
```

A CLI-replacing upgrade must run from the new release's staged CLI, not the
installed one. Uninstall on a host without DefenseClaw succeeds and changes
nothing.

`status` and `verify` also name every agent the enumerator found installed
but could not enroll (`hook_contract_unverified`, `agent_unprotected`); see
[Enrollment](/docs/enterprise/enrollment#agents-that-cannot-be-enrolled).
`include_groups` and `exclude_groups` apply on Windows as described there.

Uninstall revokes every per-user enrollment first. Once it has committed,
it removes DefenseClaw's own hook registrations and plugins (Amp,
Antigravity, Devin, Hermes, OpenCode, and a DefenseClaw Copilot user hook
file) from the agent configuration of every signed-in user, running as that
user. Only DefenseClaw's entries are removed; the user's own hooks and
settings stay. Cleanups the guardian still owed to revoked users are
included.

Acting as a user needs that user's session token, which only LocalSystem
can obtain. An MDM uninstall runs as LocalSystem (Intune install behavior
**System**). An uninstall run from an elevated administrator prompt, or from
Add/Remove Programs, cannot act as other users, so it removes no per-user
registrations. Users who are signed out during the uninstall keep theirs as
well: no guardian is left to clean them at their next sign-in. The uninstall
result names what stays: the `user_registrations_pending` warning lists each
connector and user SID it could not act as, and `user_registrations_failed`
lists removals that failed. To clean every user, run the uninstall as
LocalSystem while they are signed in.

What stays is inert. Uninstall has already revoked every enrollment. The
OpenCode and Amp plugins stop enforcing once uninstall removes
`C:\ProgramData\Cisco\DefenseClaw-HookRuntime` and the install marker. The
Devin, Hermes and Antigravity hooks point at the removed
`defenseclaw-hook.exe`, so each hook call fails to start. None of these
agents blocks on that: Devin blocks only on exit code 2 (a missing command
exits 127), and Hermes and Antigravity do not enforce a nonzero hook exit. A
DefenseClaw Copilot user hook that stays fails open, like every Copilot
integration failure.

## Review the audit log

The gateway service owns the local audit database under
`C:\ProgramData\Cisco\DefenseClaw\runtime`. Export it from an elevated
Administrator prompt, or as LocalSystem from an MDM script:

```powershell title="Elevated Administrator prompt"
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' audit export --connector claudecode -o C:\Temp\audit-claudecode.jsonl
```

On a standalone host, `audit export` run this way reads the managed
deployment's configuration and audit database read-only beside the running
gateway; it needs no environment variables. Standard accounts cannot read
the managed audit log, and the command tells them to use an elevated prompt.
Omit `--connector` to export every row. The output file must not exist
yet; it takes the permissions of its folder, so write it to a folder only
administrators can read. Treat it as sensitive: it can hold prompt and tool
content.

## Recover a pending transaction

A lifecycle that fails normally rolls back. If the rollback itself cannot
finish, the transaction stays pending: the result reports
`transaction_pending: true`, the DefenseClaw services stay stopped, and
vendor machine policy the transaction had already published can still point
at the stopped gateway. `status` shows the state; `verify` refuses until the
transaction is recovered. The failed result names the command to run next.

Recover by running DefenseClaw Setup as LocalSystem (Intune install behavior
**System**, or another MDM's system context). `/ensure` recovers the pending
transaction and then installs or upgrades; `/uninstall` recovers it and
removes the deployment:

```powershell title="As LocalSystem"
DefenseClawSetup-Enterprise-Standalone-x64.exe /ensure CONFIG=C:\Staging\config.yaml JSON=1
DefenseClawSetup-Enterprise-Standalone-x64.exe /uninstall JSON=1
```

`/repair` also recovers the transaction; after a failed first install it
then stops with "run Install", so `/ensure` is the one-step command. Outside
an MDM, a one-time scheduled task that runs as SYSTEM gives the same context.
From a protected staged copy of a release (as in [Install or
converge](#install-or-converge)), `"$Stage\defenseclaw.exe" enterprise windows
ensure` (or `repair`, `uninstall`) with the same `--profile`, trust and
`--config` options, run as LocalSystem, works the same way.

Recovery first uses the gateway the pending transaction staged. When that
gateway cannot restore or retire the transaction's managed-hook state, or
cannot remove the per-user runtime roots the transaction created (the
target-runtime rollback cleanup), for example a release whose defect caused
the failure, the standalone lifecycle
retries that step once with the `defenseclaw-gateway.exe` that ships in the
running Setup's payload (or beside the staged `defenseclaw.exe`), and only
when all of these hold:

- the lifecycle runs as LocalSystem;
- that gateway passes the same checks an install applies to its payload: an
  administrator-owned source on a local NTFS volume and the deployment's
  trust mode (a valid Authenticode signature, limited to the allowed signers
  when any are set, or the SHA-256 the payload manifest pins);
- it is not the gateway that already failed, and it is not inside the
  install root;
- it is the same release as the gateway that failed or a newer one, read
  from each gateway's version resource (an older Setup never recovers a
  newer release's transaction);
- the run is not an `--allow-unsigned` certification run.

The verified gateway is copied to `C:\Program Files\Cisco\DefenseClaw\bin`,
where the hidden command must run, and the step runs again; the rollback
then restores that file to its state before the transaction. The result and
`enterprise-lifecycle.log` record a `recovery_gateway_fallback` warning with
the binary, where it was copied from, its SHA-256, the trust basis, its
release and the staged gateway's release, the account, and the staged
gateway's failure. When recovery declines the
fallback, a `recovery_gateway_not_used` warning gives the reason
(`not_local_system`, `untrusted`, `same_binary`, `older_release`,
`version_unknown`, `no_payload`, `inside_install_root`, `unsigned_scope`)
and the staged gateway's error stands. A failure that concerns file permissions is reported in plain terms;
the internal detail is kept in a `lifecycle_diagnostic` warning for support.
Do not edit DefenseClaw files or permissions by hand to recover.

Recovery then restarts the restored release, and its gateway starts only
after that release's guardian publishes full coverage. When the restored
release is the one that cannot (for example, its guardian cannot republish a
user's lost per-user state), every recovery would fail the same way. Under
the same conditions as above, the standalone lifecycle instead finishes the
recovery with the restored release stopped and disabled and records a
`recovery_activation_deferred` warning (the restored and the Setup's
releases, the Setup gateway's SHA-256 and trust basis, and the coverage
failure). `/ensure` then upgrades to the running Setup's release in the same
run; its gateway also starts only after full coverage. `/repair` stops at
that point with the next step, because it reapplies the installed release
that could not start. With the same release, or from an elevated
administrator prompt, recovery keeps the coverage failure and a
`recovery_gateway_not_used` warning gives the reason.

## Per-user installs

On a host with the marker key, `install.ps1`, `defenseclaw upgrade` and a
per-user gateway refuse to run. `coexistence.per_user_install: migrate`
(the default) removes DefenseClaw-owned per-user hook registrations and
autostart entries after backing them up; `block` makes `ensure` fail until
they are removed; `ignore` leaves them.

## Connectors

Codex, Claude Code, Cursor and GitHub Copilot use vendor machine policy (see
[Machine policy](/docs/enterprise/machine-policy)). Other supported
connectors are registered per user and point at the administrator-owned
`defenseclaw-hook.exe --enterprise-managed`. OpenHands and Omnigent are not
supported on native Windows and are refused with a reason.
