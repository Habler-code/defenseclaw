The hook enumerator decides which users and connectors the guardian
protects. It writes the protected target manifest; administrators do not
author it by hand unless they choose `enrollment.mode: manifest`.

## How users are found

| Platform | Accounts | Source |
| --- | --- | --- |
| Windows | Local, Active Directory, and Microsoft Entra ID interactive accounts | `HKLM\...\ProfileList`, filtered to interactive user SIDs with a real, reparse-free profile |
| Linux | Local, LDAP, SSSD, Active Directory, NIS, systemd-userdb | NSS through the root-owned `getent`, logged-in sessions, home owners under the home roots, and `include_users` |
| macOS | Local, directory-bound and mobile accounts | Open Directory through libSystem, `dscl . -list /Users`, logged-in sessions, home owners under `/Users`, and `include_users` |

A connector row is added automatically when that user has a supported
version of the agent. On Linux and macOS the version is discovered by a
worker running as the user, never by root.

Discovery looks in the usual per-user install locations and in the layouts
of the common Node version managers and package managers:

| Platform | Also searched |
| --- | --- |
| Linux and macOS | nvm, fnm, Volta, asdf and mise Node installs, pnpm and yarn global directories, the npm prefix set in the user's `~/.npmrc`, Linuxbrew, the machine prefixes `/usr/local`, `/usr` and `/opt/homebrew`, and `agent_prefixes` |
| Windows | nvm-windows, fnm, Volta and pnpm installs, yarn's global directory, and the npm prefix set in `%USERPROFILE%\.npmrc` when it is inside the profile (read by the enumerator as static files; nothing is executed) |

## Filters

```yaml
enterprise:
  enrollment:
    mode: auto                 # auto: the enumerator publishes rows; manifest: you supply them
    include_users: [alice]     # add users even when discovery does not see them
    exclude_users: [build]     # never enroll
    include_groups: [developers]
    exclude_groups: [contractors]   # exclude wins over include
    exempt_users: [svc-release]     # allowed without enrollment, still inspected and logged
    unenrolled_users: inspect  # inspect | deny
    root: inspect              # inspect | deny | exempt
    uid_min: 1000              # Linux and macOS; 0 reads UID_MIN from login.defs
    uid_max: 0                 # 0 bounds only local accounts by login.defs UID_MAX
    home_roots: [/srv/home]    # extra home parents beyond the defaults
    agent_prefixes: [/opt/tools]    # extra administrator install prefixes for agent CLIs
```

- **`unenrolled_users`** applies to connectors DefenseClaw publishes through
  vendor machine policy: those hooks run for every user on the machine, so
  `inspect` (the default) inspects an unenrolled user rather than blocking
  them. `deny` refuses users without a protected enrollment. Per-user
  connectors always require enrollment.
- **`exclude_users`** and **`exempt_users`** entries match an account name or,
  on Linux and macOS, its numeric uid (for example `"1234401103"`), which is
  the spelling the gateway uses for directory accounts it cannot name.
- **`uid_max`** caps enrolled uids for local and directory accounts alike.
  With the default `0`, login.defs `UID_MAX` bounds only accounts in
  `/etc/passwd`: directory accounts (SSSD id-mapping, FreeIPA ranges) and
  systemd-homed users usually have uids above it and are still enrolled. On
  Linux, systemd's dynamic service uids (61184-65519) are never enrolled.
- **`home_roots`** adds home parents beyond the defaults (`/home` and
  `/var/home` on Linux, `/Users` on macOS). The lifecycle widens the guardian
  unit to exactly these paths. System directories such as `/`, `/etc`, `/opt`
  or `/tmp` are rejected, and any home under a world-writable ancestor is
  refused.
- **`agent_prefixes`** adds administrator install prefixes (for example an
  npm `--prefix` such as `/opt/tools`) to the places the enumerator and the
  guardian look for agent CLIs. Discovery covers per-user install locations
  and `/usr/local`, `/usr` and `/opt/homebrew`; an agent installed anywhere
  else is not enrolled, so its per-user connector gets no hooks, and with
  `unenrolled_users: deny` its machine-policy connector refuses that user.
  Paths under homes and temporary directories are rejected.

Group filters on Windows cover local groups, Active Directory groups and
Microsoft Entra ID groups. Name a group by SID (`S-1-5-32-544`,
`S-1-12-1-...`) or by name (`Administrators`, `CONTOSO\Developers`); list
Entra ID groups by SID, because the device cannot resolve their names.
Membership comes from:

- the signed-in user's session token, which lists every group they belong
  to. The enumerator caches it, so a signed-out user is decided from the
  membership seen at their last sign-in, and a change made while they are
  signed out applies when they next sign in;
- for local groups, the local account database, which lists direct members
  at any time, so local accounts are always decided.

A directory user whose membership is not known this way (they have not
signed in since DefenseClaw was installed) is **pending**: their existing
rows are kept, no new rows are added, and nothing is revoked until they next
sign in. Well-known groups other than Everyone (Authenticated Users,
INTERACTIVE and the like) are added to a token at sign-in and listed by no
account database, so for them a signed-out user without a cached token is
pending too.

A group name that does not resolve and never resolved before (a
misspelling, a group of another platform such as `wheel` in a config shared
with Linux, or a directory group on a laptop that has been off the corporate
network since installation) cannot be evaluated. In `exclude_groups` it
excludes no one, as on Linux and macOS. In `include_groups` it leaves every
user that no other entry admits pending, so it never revokes anyone. The
enumerator logs the entry every cycle, and a signed-in user left pending has
their installed agents reported as `agent_unprotected`. Name groups by SID to
avoid lookups.

## Agents that cannot be enrolled

When the enumerator finds an agent installed for an eligible user but cannot
enroll it, it records the agent, and `status` and `verify` report it with
`security_complete: false`. Status warns; verify fails.

| Code | Meaning |
| --- | --- |
| `hook_contract_unverified` | The installed version has no verified DefenseClaw hook contract |
| `agent_unprotected` | The agent's version could not be read, it is below the platform minimum, its user's home is untrusted (Linux and macOS), its signed-in user's enrollment is pending (Windows), a Claude Code change to an older hook contract was not followed (Windows), or (Windows) it is not installed where the guardian can manage it |

A per-user connector in this state runs without DefenseClaw hooks. A
machine-policy connector refuses the unenrolled user on Windows, and on
Linux and macOS with `unenrolled_users: deny`.

On Linux and macOS a user who has never been enrolled and whose home is
untrusted (group- or other-writable, a symlink, owned by another account, or
covered by a user mount) gets no rows. The enumerator still lists the agents
installed for them, as that user and without running anything in that home
(package metadata and the presence of the agent CLIs), and reports each one.
Remove group and other write from the home to enroll the user. An enrolled
user who loosens their home keeps their rows, and their worker removes group
and other write again before the next repair.

Discovery only covers the locations above. An agent CLI installed anywhere
else in a user's home (a custom `NVM_DIR`, `XDG_DATA_HOME` or `PNPM_HOME`, an
`npm --prefix` given on the command line, or a binary copied into an
arbitrary directory) is not found, so it is neither enrolled nor reported.
Install shared agents under an `agent_prefixes` path (Linux and macOS), and
use application control where users must not run agents from arbitrary
locations.

## Agent upgrades

The enumerator reads each enrolled user's agent version again every cycle
(on Windows, while the user is signed in, so the guardian can repair their
hooks at once). When the version changes to one with a verified hook
contract, the guardian re-renders and re-verifies that user's hooks for it.
A version without a verified contract is not followed: on every platform the
row keeps its last verified version, so the guardian keeps repairing the
hooks rendered for it, and `status` and `verify` report
`hook_contract_unverified` until the user returns to a verified version or
DefenseClaw adds the contract.

A user controls the version their own install reports, so they can move
their own rows between verified contracts, but never to a version without
one. On Windows the one machine-wide Claude Code policy is rendered from the
oldest contract among the enrolled Claude Code rows, so an enrolled user's
change to an older Claude Code contract is not followed either: the row
stays at its version, the change is reported as `agent_unprotected`, and no
other user's policy changes. A user enrolled for the first time with an
older Claude Code still sets the oldest contract.

## Unavailable homes

A home that is not mounted, locked (ecryptfs, FileVault before login), on an
unreachable network share, or denied to root by NFS `root_squash` is
**deferred**, not failed. The row stays and is retried every cycle. The
worker reads such homes with the user's own credentials, so `root_squash`
homes work once they are mounted.

## Deleted and changed users

- Only a definitive "no such user" answer counts. A directory outage, a
  timeout or an unreachable server never revokes anyone.
- A row is revoked after several consecutive definitive misses.
- A reused uid, or a home recreated with a different inode, is treated as a
  new identity and enrolled from scratch.
- Windows keeps an existing disabled row disabled across cycles.
- On Windows, when a user's per-user row is revoked (the user is excluded,
  deleted, or the connector is disabled), the guardian removes DefenseClaw's
  own hook registration or plugin from that user's agent configuration,
  running as the user; the user's own hooks stay. A signed-out user has no
  session to act under, so the cleanup is recorded and runs at their next
  sign-in. That includes a user whose profile folder is absent while they
  are signed out (a roaming profile whose local copy is deleted, or an
  FSLogix container); the record is dropped without a cleanup only when the
  account is gone too. A user who is enrolled again before then keeps the
  record until the guardian has reinstalled and protects them, so a second
  revocation before that still cleans them.

## New users

A user created after installation is enrolled on the next enumerator cycle
(five minutes) once they have a supported agent. Until then, a per-user
connector's hook fails closed with an enrollment message, and a
machine-policy connector's hook inspects them (`unenrolled_users: inspect`).
