Enterprise deployment runs DefenseClaw as operating-system services that
belong to the administrator, not to the person running Codex, Claude Code,
Cursor or another AI agent. The agent's hooks still run in the user's
session, but the gateway that decides on each tool call, the policy it
enforces, and the service that repairs the hooks are all out of the user's
reach.

{/* verify-after-merge: M2 M4 M5 M6 — this section documents the standalone profile being merged into the enterprise-hardening branch */}

<Callout title="Two profiles">
`managed_enterprise` has two profiles. **Secure Client** is installed by Cisco
Secure Client and uses Cisco AI Defense through Secure Client's cloud
identity. **Standalone** is installed by any MDM, a package manager or an
administrator, runs the full local policy engine, and can add Cisco AI Defense
with an API key. This section covers the standalone profile. The Secure
Client profile is unchanged; see [Enterprise hardening and deployment](/docs/setup/enterprise-deployment).
</Callout>

## Profiles

| | Secure Client | Standalone |
| --- | --- | --- |
| Installed by | Cisco Secure Client | Intune or any MDM, a `.deb`/`.rpm`/`.pkg`, or an administrator shell |
| Platforms | Windows, macOS | Windows, Linux, macOS |
| Decisions | Cisco AI Defense only | Local engine (rule packs, policy, CodeGuard, judge when keyed) plus Cisco AI Defense when an API key is stored |
| If AI Defense is unreachable | Secure Client posture | The local verdict stands |
| Windows services | Gateway, CMID broker, sensor helper, guardian, enumerator | Gateway, sensor helper, guardian, enumerator |
| Lifecycle | Windows PowerShell 5.1 · macOS shell installer | PowerShell 7 on Windows · Go on Linux and macOS |

The profile is set in the administrator's config and pinned in every service
environment (`DEFENSECLAW_ENTERPRISE_PROFILE`). The two must agree, and the
profile cannot change without reinstalling. When nothing is set, Windows and
macOS resolve to Secure Client and Linux resolves to standalone. The two
profiles never share a host.

## What a normal user cannot do

- Stop, disable or reconfigure a DefenseClaw service, or replace its binary.
- Edit the config, policies, secrets, target manifest or authorization
  ledger, or read the AI Defense key.
- Turn off DefenseClaw's hooks for Codex or Claude Code through their own
  settings: DefenseClaw sets the vendors' managed-hooks-only locks.
- Add a user- or project-level hook that rewrites a tool call after
  DefenseClaw inspected it: the [foreign-hook guard](/docs/enterprise/foreign-hook-guard)
  removes or blocks it.
- Impersonate the gateway: the hook sends nothing until the operating system
  proves the listener is the DefenseClaw service.
- Install a per-user DefenseClaw that competes with the managed one.

A user can still delete files they own, such as a per-user hook
registration. The guardian repairs those within one reconcile cycle; vendor
machine policy, where it exists, has no such window.

## Configuration

The standalone config uses the same keys on every OS. Only the administrator
can edit it.

```yaml title="config.yaml (standalone excerpt)"
config_version: 8
deployment_mode: managed_enterprise
enterprise:
  profile: standalone
  inspection:
    ai_defense:
      enabled: false                # true after `enterprise secret set`
      credential: ai-defense-api-key
  enrollment:
    mode: auto                      # auto | manifest
    include_users: []
    exclude_users: []
    include_groups: []
    exclude_groups: []
    exempt_users: []
    unenrolled_users: inspect       # inspect | deny
    root: inspect                   # inspect | deny | exempt
  machine_policy:
    default:
      ownership: merge              # merge | verify_only | off
      managed_hooks_only: enforce   # enforce | preserve
      foreign_hooks: remove         # remove | report | allow
    connectors:
      claudecode:
        higher_precedence_sources: fail   # fail | warn
  trust:                            # Windows payload trust
    # mode: hash_pinned             # hash_pinned | authenticode; leave unset for the default, see below
    allowed_signers: []
  coexistence:
    per_user_install: migrate       # migrate | block | ignore
    disable_self_update: true
  network:
    https_proxy: ""
    no_proxy: ""
guardrail:
  enabled: true
  mode: observe
```

`config_version: 8` is required. `guardrail.rule_pack_dir` is optional:
without it the gateway uses the product's default rule packs. A directory you
name must exist and be writable only by administrators. DefenseClaw Setup
checks the file with the gateway's own compiler before it changes anything
and names the line and the reason when the gateway could not load it.

`enterprise.network` is the gateway's outbound proxy. With `https_proxy` set,
the gateway reaches AI Defense, LLM providers (the judge and the guardrail
proxy), the LLM passthrough, webhooks, the remote model router and telemetry
exporters (OTLP over HTTP and gRPC, Splunk HEC, HTTP JSONL) through it, and
sets `HTTPS_PROXY`/`NO_PROXY` for its other HTTPS clients. `no_proxy` lists
hosts, domains and CIDRs that connect directly; loopback always does. The
gateway opens an HTTP `CONNECT` tunnel to the destination host name, so the
proxy's host rules apply and TLS stays end to end. Webhook, passthrough and
telemetry destinations still pass the gateway's address check first, so their
host names must resolve on the device. The proxy URL cannot carry
credentials, and LLM provider connections need an `http://` proxy URL: with an
`https://` one the gateway refuses those calls rather than connecting
directly. The gateway reads `enterprise.network` when it starts, so a config
reload that changes it is reported as restart-required and the gateway keeps
the previous proxy until it restarts.

`enterprise.trust` applies on Windows. `mode: authenticode` admits only
Authenticode-signed payloads, so the Windows lifecycle refuses with exit code
`1639`, before any change:

- a hash-pinned run, such as the unsigned
  `DefenseClawSetup-Enterprise-Standalone-x64.exe` (it passes
  `--trust-mode hash_pinned`), whether the config is supplied or already
  installed;
- an install, upgrade, repair or `ensure` over a deployment that was installed
  hash-pinned. That deployment keeps admitting its installed payload by the
  recorded SHA-256 pins, so it stays hash-pinned. To move it to
  `authenticode`, remove it with `uninstall --purge` and install a signed
  Setup.

If you deploy the unsigned Setup, set `mode: hash_pinned` or leave `mode`
unset; an empty `mode: ""` is not a valid value. `allowed_signers` restricts signed payloads to the listed signer
certificates, like `--allowed-signer`.

`enterprise.coexistence.disable_self_update` controls only the Windows
`HKLM\SOFTWARE\Policies\Cisco\DefenseClaw\DisableSelfUpdate` policy value,
which also stops the per-user installer on that computer. Setting it to
`false` does not bring back update notices or `defenseclaw upgrade` on any
OS: on every host with a managed deployment the notice stays off and
`defenseclaw upgrade` and `rollback` refuse.

An inline `cisco_ai_defense.api_key` is rejected in the standalone profile.
Store the key with `defenseclaw-gateway enterprise secret set --name
ai-defense-api-key --from-stdin`. The value is read from standard input and
never printed; `enterprise secret status` shows only whether it is present,
when it changed, and a digest prefix. On Windows the same command writes
`C:\ProgramData\Cisco\DefenseClaw\secrets\<name>` with the protected DACL.
